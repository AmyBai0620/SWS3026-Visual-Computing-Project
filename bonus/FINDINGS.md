# Bonus Level Task 1 — 实验结论与答辩讲稿

## 0. 流水线概览(一句话背景)

Task 1 的目标是把参考视频里的舞者姿态稳定地提取出来。检测主干沿用官方示例给的 **YOLOv8n-pose**,输出 COCO-17 关键点。我们没有换模型,而是在它输出之后补了一层后处理:

```
frame → YOLOv8n-pose → 关键点置信度过滤 → 主舞者选择 → 时序平滑 → 渲染
```

代码组织:

```text
bonus/
├── danceapp.py           # 官方原版,保持不动,用于 before 演示
├── pose_pipeline.py      # 核心:PoseTracker + 渲染,不依赖 GUI
├── danceapp_v2.py        # 接入 pipeline 的 GUI 版本
├── make_task1_figs.py    # 生成 task1_compare.png / task1_stats.txt
└── task1_ablation.py     # 消融实验
```

`pose_pipeline.py` 刻意做成无 GUI 依赖,Task 2 的参考视频和摄像头两路可以直接复用同一个 `PoseTracker`。

## 1. 原版代码在哪里失败(细则第 11–12 题的证据)

测试片段:`dance_example_1.mp4`(1280×720,30 fps,89 秒),取前 550 帧。

| 现象 | 实测数据 |
|---|---|
| 帧中检出 >1 人 | **191 / 550 帧(35%)** |
| 帧中检出 0 人 | 92 / 550 帧(片头片尾) |
| 单帧推理耗时 | 均值 **54 ms**,p95 60 ms |
| 可达帧率 | **18.4 fps**(视频需要 30 fps) |

由此定位到原版 `danceapp.py` 的三个问题:

### 问题 1:把背景误检成人,并给它画骨架

原版 [danceapp.py:130](danceapp.py#L130) 对 `results` 里**每一个**检出目标无差别绘制。在 f412 / f481 / f549,YOLO 把画面右侧的**窗帘与绿植**误检成了第二个人,于是屏幕右边出现一条凭空的绿色骨架(见 `task1_compare.png` 左列)。

这比"路人入镜"更值得讲:干扰不一定来自真人,低置信度的**背景误检**同样会污染画面,而且它在 Task 2 里会直接把评分算错。

### 问题 2:关键点置信度被完全忽略

原版用 `keypoints.xyn` 取归一化坐标,但从未读取 `keypoints.conf`。YOLO 对遮挡或出画的关节返回 `(0, 0)`,乘回宽高后仍是 `(0, 0)`,会在**画面左上角堆出一簇红点**并甩出横跨全屏的骨架线。

诚实说明:在 `dance_example_1.mp4` 上这个问题**没有触发**(舞者全身入镜,采样帧的 `(0,0)` 关键点计数为 0)。它主要在**摄像头半身入镜**时爆发,所以留到 Task 2 的 demo 里展示更有说服力。

### 问题 3:视频按推理速度播放,而不是按自己的帧率

原版 [process_video_file](danceapp.py#L101-L109) 读一帧、推理一帧、显示一帧,没有任何时钟控制。CPU 上推理只有 18.4 fps,所以 30 fps 的视频会被**放慢到 0.6 倍速**播放。另外它在工作线程里直接 `label.configure()` 更新 Tk 控件,这不是 Tkinter 支持的用法,长时间运行会出现界面卡顿甚至崩溃。

## 2. 我们做了什么(细则第 12 题的答案)

### 2.1 关键点置信度过滤
`conf < 0.5` 的关键点标记为无效,**骨架连线要求两端点都有效**才画。另外额外拦截"高分但落在原点"的退化情况。

### 2.2 主舞者选择
对每个检出目标打分:

```
score = sqrt(bbox面积 / 画面面积) × 平均关键点置信度 × 中心度
```

- 面积开平方,避免面积项一家独大
- 中心度只做**弱偏好**(系数 0.5),因为舞者并不总在正中
- 取最高分者作为主舞者

### 2.3 时序关联(防止在两人之间跳)
再乘一个连续性奖励:与上一帧选中目标的中心距越近,奖励越高(最高 ×1.8,超过画面对角线 1/3 后衰减为 0)。

### 2.4 EMA 时序平滑
对**本帧与上帧都有效**的关键点做指数滑动平均,`alpha = 0.6`。只平滑共同有效的点,避免把无效点的坐标混进来。

### 2.5 短时丢失保持
检测失败时沿用上一帧姿态,最多保持 5 帧,超过则清空。避免舞者快速转身时骨架频繁闪断。

### 2.6 播放时钟与线程安全
`danceapp_v2.py` 按视频自身 fps 计算目标帧号,落后时用 `cap.grab()` **丢帧追进度**(grab 不解码,跳帧几乎零成本),保证视频始终以正常速度播放。工作线程只把结果放进 `queue`,由 Tk 主循环 `after()` 取出更新控件。

## 3. 消融实验:每一步各值多少(`task1_ablation.txt`)

同一段 550 帧,三种配置:

| 配置 | 身份跳变次数 | 关键点帧间位移中位数 (px) |
|---|---:|---:|
| A 朴素(无时序关联、无平滑) | 0 | 5.75 |
| B + 时序关联 | 0 | 5.75 |
| C + EMA 平滑 | **0** | **4.91** |

**如实结论:**

- **EMA 平滑有效**,抖动下降约 **15%**(5.75 → 4.91 px)。
- **时序关联在这个视频上没有产生差异**。原因很清楚:干扰目标是窗帘误检,它的面积和关键点置信度都远低于真人,单靠"面积 × 置信度"已经稳定选对,连续性奖励从未成为决定因素。它是为**两个体型相近的真人同框**准备的保险,需要拿 TikTok 数据集里的多人片段才能验证其价值。

答辩时这一条不要说成"我们的时序关联解决了跳人问题",而应说成"我们设计了时序关联作为多人场景的保险,并用消融实验确认了在当前单人片段上它不是决定因素"。这是更强的表述,因为它显示我们**验证过**而不是**假设过**。

## 4. 实时性

| 指标 | 数值 |
|---|---|
| YOLOv8n-pose 单帧(CPU,imgsz=640) | 54 ms |
| 可达帧率 | 18.4 fps |
| 视频帧率 | 30 fps |

CPU 上跑不到 30 fps。当前策略是**丢帧保时序**——保证播放速度正确,牺牲部分帧不做检测。这个取舍对 Task 2 是必要的:评分依赖参考视频和摄像头的**时间对齐**,宁可少算几帧也不能让视频变慢。

若需提速的备选:降 `imgsz` 到 480、隔帧检测 + 中间帧插值、或换 GPU 环境。
