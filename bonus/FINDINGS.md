# Bonus Level Task 1 — 实验结论与答辩讲稿

## 0. 流水线概览(一句话背景)

Task 1 的目标是把参考视频里的舞者姿态稳定地提取出来。检测主干沿用官方示例给的 **YOLOv8n-pose**,输出 COCO-17 关键点。我们没有换模型,而是在它输出之后补了一层后处理:

```
frame → YOLOv8n-pose → 关键点置信度过滤 → 主舞者选择 → 时序平滑 → 渲染
```

代码组织:

```text
bonus/
├── danceapp.py           # 官方原版,保持不动,用于 before 演示
├── pose_pipeline.py      # 核心:PoseTracker + 渲染,不依赖 GUI
├── danceapp_v2.py        # 接入 pipeline 的 GUI 版本
├── make_task1_figs.py    # 生成 task1_compare_<name>.png / task1_stats_<name>.txt
├── task1_ablation.py     # 消融实验,可指定视频
└── video/                # 6 个参考视频(单人 / 主舞者+路人 / 群舞)
```

两个脚本都接受视频名参数,例如 `python make_task1_figs.py dance_example_2`,输出文件按视频名加后缀。

`pose_pipeline.py` 刻意做成无 GUI 依赖,Task 2 的参考视频和摄像头两路可以直接复用同一个 `PoseTracker`。

## 1. 原版代码在哪里失败(细则第 11–12 题的证据)

我们用 `video/` 下 6 个视频测试,覆盖三种难度(每帧 25 采样点统计人数):

| 视频 | 分辨率 | 人数(min–max) | 场景 |
|---|---|---|---|
| dance_example_5 | 786×1384 | 1–1 | 干净单人对照 |
| dance_example_1 | 1280×720 | 0–2 | 单人 + 窗帘误检 |
| dance_example_6 | 764×1364 | 1–2 | 轻度多人 |
| dance_example_3 | 788×1386 | 1–4 | 单人 + 短暂路人 |
| **dance_example_2** | 610×1082 | **1–7** | **主舞者 + 背景路人(真实 TikTok)** |
| **dance_examle_4** | 1804×1050 | **5–7** | **群舞,每帧多人** |

由此定位到原版 `danceapp.py` 的三个问题:

### 问题 1:多人 / 背景误检时给所有目标都画骨架

原版 [danceapp.py:130](danceapp.py#L130) 对 `results` 里**每一个**检出目标无差别绘制。两类污染:

- **背景误检**:`dance_example_1` 里 YOLO 把画面右侧的**窗帘与绿植**误检成第二个人(见 `task1_compare_dance_example_1.png`),35%(191/550)的帧出现 >1 目标。
- **真人多人**:`dance_example_2`(主舞者+路人)有 **588/661 帧多人**,`dance_examle_4`(群舞)**531/531 帧全是多人**,最多同框 7 人(见 `task1_compare_dance_examle_4.png` 左列,5–7 具骨架同时画出)。

Task 2 的评分依赖单一舞者的关键点,原版这种"全画"方式会直接把评分算错——你根本不知道该拿哪具骨架去和参考视频对比。

### 问题 2:关键点置信度被完全忽略

原版用 `keypoints.xyn` 取归一化坐标,但从未读取 `keypoints.conf`。YOLO 对遮挡或出画的关节返回 `(0, 0)`,乘回宽高后仍是 `(0, 0)`,会在**画面左上角堆出一簇红点**并甩出横跨全屏的骨架线。

诚实说明:在 `dance_example_1.mp4` 上这个问题**没有触发**(舞者全身入镜,采样帧的 `(0,0)` 关键点计数为 0)。它主要在**摄像头半身入镜**时爆发,所以留到 Task 2 的 demo 里展示更有说服力。

### 问题 3:视频按推理速度播放,而不是按自己的帧率

原版 [process_video_file](danceapp.py#L101-L109) 读一帧、推理一帧、显示一帧,没有任何时钟控制。CPU 上推理只有 18.4 fps,所以 30 fps 的视频会被**放慢到 0.6 倍速**播放。另外它在工作线程里直接 `label.configure()` 更新 Tk 控件,这不是 Tkinter 支持的用法,长时间运行会出现界面卡顿甚至崩溃。

## 2. 我们做了什么(细则第 12 题的答案)

### 2.1 关键点置信度过滤
`conf < 0.5` 的关键点标记为无效,**骨架连线要求两端点都有效**才画。另外额外拦截"高分但落在原点"的退化情况。

### 2.2 主舞者选择
对每个检出目标打分:

```
score = sqrt(bbox面积 / 画面面积) × 平均关键点置信度 × 中心度
```

- 面积开平方,避免面积项一家独大
- 中心度只做**弱偏好**(系数 0.5),因为舞者并不总在正中
- 取最高分者作为主舞者

### 2.3 时序关联(防止在两人之间跳)
再乘一个连续性奖励:与上一帧选中目标的中心距越近,奖励越高(最高 ×1.8,超过画面对角线 1/3 后衰减为 0)。

### 2.4 EMA 时序平滑
对**本帧与上帧都有效**的关键点做指数滑动平均,`alpha = 0.6`。只平滑共同有效的点,避免把无效点的坐标混进来。

### 2.5 短时丢失保持
检测失败时沿用上一帧姿态,最多保持 5 帧,超过则清空。避免舞者快速转身时骨架频繁闪断。

### 2.6 播放时钟与线程安全
`danceapp_v2.py` 按视频自身 fps 计算目标帧号,**双向**校时:落后时用 `cap.grab()` **丢帧追进度**(grab 不解码,跳帧几乎零成本);超前时 `sleep` 等到该帧应出现的时刻。工作线程只把结果放进 `queue`,由 Tk 主循环 `after()` 取出更新控件。

> **踩坑记录(值得讲)**:最初只写了"落后就跳帧",漏了"超前就等待"。在本机 CPU 上看不出问题——推理只有 18 fps,永远追不上 30 fps 的视频,**慢推理恰好充当了节流器**。这个漏洞直到 Task 2 才暴露:那里参考视频用的是**预计算骨架、不跑推理**,没有任何东西拖慢循环,于是视频被快进。修好 Task 2 后我们回头把 `danceapp_v2` 也补齐了,否则换到 GPU 机器同样会快进。

### 2.7 GUI 显示问题的修复

实测中还暴露了三个纯显示层的问题,一并修掉:

1. **画面被拉伸变形**:原来把画面硬缩放到固定面板尺寸,不保宽高比,4:3 的摄像头塞进竖面板就被压瘦。改用 `pose_pipeline.fit_letterbox()`——按**较小的缩放比**缩放并补黑边,绝不拉伸。
2. **面板尺寸写死,放大窗口只留白边**:改成两个面板随窗口 `fill=BOTH, expand=True` 自适应,图片按面板实时尺寸生成。
3. **参考面板会逐渐吞掉摄像头面板**(2 的后遗症,严重):Tk 里一个显示图片的 Label 会**请求**这张图那么大的尺寸,而**几何传播默认开启**,于是"图变大 → Frame 被撑大 → 下一帧图更大"形成正反馈,参考面板一路膨胀直到摄像头消失。解法是给两个 Frame 设定初始尺寸并 **`pack_propagate(False)`**,把它们锁死在各占 50%,切断反馈链。
   *验证*:无头测试里只往左面板猛塞 1280×720 大图 40 帧,两侧宽度稳定在 520 / 508 px,不再被吞。

另外删掉了原来那个 "Show/Hide Video" 按钮(切换纯白底/视频底,对这个对照 demo 没有意义,还容易误触)。

## 3. 消融实验:每一步各值多少(`task1_ablation_*.txt`)

三种配置,在三个难度递增的视频上跑。**身份跳变**定义为选中目标的中心在相邻帧跳动超过画面对角线的 15%(即"这一帧换人了"),阈值随分辨率自动缩放。

| 视频 | 配置 | 身份跳变 | 关键点帧间位移中位数 (px) |
|---|---|---:|---:|
| dance_example_1(单人+窗帘) | A 朴素 | 0 | 5.75 |
| | B +时序关联 | 0 | 5.75 |
| | C +EMA 平滑 | **0** | **4.91** |
| dance_example_2(主舞者+路人) | A 朴素 | **32** | 6.82 |
| | B +时序关联 | **2** | 6.27 |
| | C +EMA 平滑 | **2** | **4.80** |
| dance_examle_4(群舞 5–7 人) | A 朴素 | **41** | 6.68 |
| | B +时序关联 | **0** | 6.25 |
| | C +EMA 平滑 | **0** | **4.95** |

**结论(现在有真人多人数据支撑):**

- **时序关联是多人场景的关键**。在真人同框时,主舞者和路人体型、置信度都相近,单靠"面积 × 置信度"会在他们之间来回跳——朴素基线在 `dance_example_2` 跳 **32 次**、群舞 `dance_examle_4` 跳 **41 次**。加上连续性奖励后分别降到 **2 次**和 **0 次**。`task1_compare_dance_examle_4.png` 可以看到 pipeline 在 4 个不同时刻稳定锁定同一个中间舞者。
- **在单人视频(dance_example_1)上时序关联不产生差异**,因为那里的干扰是低置信度窗帘误检,面积和置信度都远低于真人,单靠面积×置信度就选对了。这解释了为什么必须用多人视频才能验证它——这正是你补充这批视频的价值。
- **EMA 平滑在所有视频上都有效**,抖动稳定下降约 **13–15%**(如 6.82 → 4.80 px),且不引入身份跳变。

答辩时可以直接给这张表:**同一套策略,难度越高价值越大**——从单人 0→0,到主舞者+路人 32→2,到群舞 41→0,证明我们的设计是被数据验证过的,不是拍脑袋。

## 4. 实时性

CPU 环境(torch 2.7.1 CPU 版),单帧耗时随**分辨率和人数**显著变化:

| 视频 | 分辨率 | 单帧均值 / p95 (ms) | 可达帧率 |
|---|---|---|---|
| dance_example_1 | 1280×720 | 54 / 60 | 18.4 fps |
| dance_example_2 | 610×1082 | 68 / 93 | 14.7 fps |
| dance_examle_4 | 1804×1050,7 人 | **174 / 472** | **5.8 fps** |

三个视频都达不到 30 fps,群舞高分辨率场景尤其慢(p95 达 472 ms)。原因:YOLO 推理成本随输入像素数上升,人越多后处理越重。

当前策略是**丢帧保时序**——按视频自身 fps 计算目标帧号,落后就跳帧、超前就等待(见 §2.6),保证播放速度正确、牺牲部分帧不做检测。这个取舍对 Task 2 是必要的:评分依赖参考视频和摄像头的**时间对齐**,宁可少算几帧也不能让视频变慢或变快。

若需提速的备选:降 `imgsz` 到 480、隔帧检测 + 中间帧插值、或换 GPU 环境。群舞这类高分辨率视频,降 `imgsz` 收益最明显。
