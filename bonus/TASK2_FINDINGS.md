## 1. 双面板程序(细则第 13 题)

`just_dance.py` 左右两个面板:

- **左(Reference)**:参考视频叠加预处理好的骨架播放。
- **右(You)**:摄像头实时画面 + `PoseTracker` 骨架 + Just-Dance 风格的大号反馈文字(PERFECT/SUPER/GOOD/X)+ 数字分。

参考播放线程是**时钟**,它持续更新当前参考时间 `t_play`;摄像头线程每处理一帧就拿当前 `t_play` 去打分。线程只把画面塞进队列,由 Tk 主循环取出更新控件(线程安全)。

### 1.1 【发现问题→解决问题】显示与播放的两个坑

搭好双面板后实测,暴露两个直接影响体验的问题:

**问题 A:摄像头和参考视频被拉伸变形(过横或太瘦)。** 原因是显示时把画面**硬缩放**到固定面板尺寸,不保宽高比——4:3 的摄像头塞进 9:16 的竖面板就被压瘦。
修复:`pose_pipeline.fit_letterbox()` 按**较小的缩放比**缩放并补黑边,绝不拉伸:

```python
scale = min(box_w / w, box_h / h)          # 取小的那个 → 一定装得下且不变形
nw, nh = round(w * scale), round(h * scale)
canvas = np.full((box_h, box_w, 3), 0, np.uint8)   # 黑底
canvas[y0:y0+nh, x0:x0+nw] = cv2.resize(frame, (nw, nh))  # 居中贴入
```

**问题 B:参考视频加速播放,模仿者根本跟不上。** 这是个**隐蔽的 bug**:参考侧用的是**预计算骨架、不跑推理**,而原来的播放循环只处理"落后就跳帧",没有"超前就等待"——于是循环以几百 fps 空转,把舞蹈快进了。(对照:Task 1 的 `danceapp_v2` 每帧都跑 YOLO,天然被拖到实时,所以没这个毛病;正是"不跑推理"让 bug 浮现。)
修复:每帧算出它**应出现的墙钟时刻**,没到就 `sleep` 等到点;落后了才跳帧追。并顺手加了**慢放选项**(1.0×/0.75×/0.5×)帮学习者跟上——`t_play` 同步放慢,评分自动对齐,无需改评分代码:

```python
due = start + pos / (fps * speed)   # 这一帧该出现的时刻(speed<1 = 慢放)
now = time.perf_counter()
if now < due:
    time.sleep(due - now)           # ← 关键:超前就等,消除快进
ret, frame = cap.read()
# ... 落后太多再 grab() 跳帧追进度
```

> 答辩点:B 是"同一套跳帧策略,在有推理/无推理两条路上表现不同"的典型——发现它需要理解**为什么 Task 1 没坏而 Task 2 坏了**。

## 2. 打分:对齐与度量(细则第 14 题)

细则第 14 题三问:**怎么打分、怎么对齐、用什么相似度/距离度量**。逐一回答:

### 2.1 空间对齐 —— 用肢体方向,天然免疫位置和体型
你和参考舞者身材不同、站位不同、离镜头远近不同,**不能直接比像素坐标**。

我们把姿态表示成 **12 根肢体的方向向量**(上/下臂、大/小腿、躯干两侧、肩线、髋线),比较两个姿态时算**对应肢体方向的夹角**。方向向量的夹角**对平移和缩放天然免疫**——小个子和大个子摆同一个姿势,夹角完全一样,不需要手工配准。

```python
v = xy[b] - xy[a]          # 肢体 a→b 的向量
units[i] = v / norm(v)     # 单位方向:丢掉长度(体型),只留朝向
```

(另外 `normalize_pose()` 提供髋部中心+躯干缩放的归一化坐标,用于可视化和距离型备选度量。)

### 2.2 相似度度量 —— 角度容差 + smoothstep
每根肢体:算用户方向与参考方向的夹角 θ,**0° 满分、到 ANGLE_TOL(50°)归零**;整体分数 = 各肢体**加权平均** × 100(手臂 1.5、腿 1.2、躯干 0.6–0.7,手脚是观众评判舞蹈的重点)。

映射函数用 **smoothstep** 而不是线性:小误差几乎不扣(容忍摄像头抖动),中段快速掉分(明显做错就重罚):

```python
def _angle_credit(angle):
    x = np.clip(1.0 - angle / ANGLE_TOL, 0.0, 1.0)
    return x * x * (3.0 - 2.0 * x)     # smoothstep:两端平、中间陡
```

为什么不用最朴素的 `(cos+1)/2`?因为它把一切人体姿态都压进高分区(两个随机方向夹角 90°、余弦 0、还有 50 分),错误动作也能骗到 90。角度容差映射区分度强得多——见 §4。

### 2.3 时间对齐 —— 单调有界的延迟跟踪窗
你总比参考视频慢半拍(PDF 明确点名)。做法:先**宽搜一次**锁定你的滞后 `lag`,之后每帧只在参考的 `t_play - lag ± 0.13s` 窄窗里找最佳匹配,并把 `lag` **钳到 ≤0.6s、缓慢自适应**:

```python
if self._lag is None:                      # 首次:宽窗 [t-0.5, t+0.2] 锁定滞后
    lo, hi = search(t - acq_back), search(t + acq_fwd)
else:                                       # 之后:只在 t-lag 附近 ±0.13s 窄窗
    c = t_play - self._lag
    lo, hi = search(c - track_half), search(c + track_half)
# 匹配后更新 lag(钳位 + 慢速 EMA),使对比目标随播放不断前移
implied = clip(t_play - ref_t[best_j], 0, max_lag)
self._lag = clip((1-lag_ema)*self._lag + lag_ema*implied, 0, max_lag)
```

**为什么这样设计而不是"宽窗取最大"**:见 §4——正是"宽窗取最大"造成了"站着不动刷 SUPER"的漏洞。这个单调前移的窗口是修复的核心。

## 3. 分数形态:数字+文字、随时间、总分(细则第 15 题)

细则第 15 题四问,逐一回答:

- **数字还是文字?两者都有**:每帧输出 0–100 数字分,同时映射成文字档 PERFECT(≥85)/ SUPER(≥70)/ GOOD(≥50)/ X。
- **随时间怎么变?** 每帧分数做 EMA 平滑(α=0.5)避免文字档频繁跳变,实时显示。见 `task2_score_timeline_dance_example_5.png`:三种舞者(好 / 时快时慢 / 错误动作)的分数曲线落在不同色带,一眼看出档位。
- **结束有总分吗?怎么算?** 有。跳完后汇总:**总分 = 全程逐帧分的平均**,并给出档位分布(多少帧 PERFECT/SUPER/GOOD/X)。`just_dance.py` 在参考视频放完时弹窗显示。
- **关键:不可评的帧计 0,不丢弃。** 用户没入镜/身体不全时,该帧记 **0 分并计入总评**(而不是跳过)。否则"难段落退出画面"就成了免罚——见 §4。

## 4.【核心思维链】我们怎么发现"站着不动能刷 SUPER",又怎么修好它

> 这是 Task 2 最能体现"发现问题→定位根因→设计修复→量化验证"的一条主线,答辩时建议重点讲。

### 4.1 现象:一个能骗过评分的玩家
实测发现一个**作弊姿势**:**人杵在那里一动不动**,系统照样频繁给 SUPER,总评能到 GOOD 偏上。一个根本没在跳舞的人不该拿高分——这说明评分机制有洞。

### 4.2 定位根因(不是一个 bug,是四个叠加)
| # | 根因 | 为什么导致刷分 |
|---|---|---|
| 1 | **时间对齐"宽窗取最大"** | 每帧在 0.7s(≈21 帧)窗口里取相似度最大的一帧。21 次带噪比对取最大,**期望本身就偏高**;你定住不动,只要参考"扫过"一个接近的姿势就命中。 |
| 2 | **只对可见肢体归一化 + 不可评帧丢弃** | 只露上半身、手臂对了就满分,腿做错/没做不扣分;难段落退出画面的帧被丢弃、不计入平均。**藏得越多分越高。** |
| 3 | **容差 70° 太松 + 线性衰减** | 偏 60° 的胳膊还有分;"随便站直"就能到 50–60,分数全挤在高位、拉不开档。 |
| 4 | **2D 前缩肢体方向不稳** | 肢体指向镜头时投影趋近一点,方向被噪声主导,凭空丢/给分。 |

### 4.3 四个修复(逐一对应根因)

**修复 1 —— 单调有界的延迟跟踪窗(替代宽窗取最大)+ 活跃度门。** 这是杀掉"站着不动"的主力,两招合力:
- *单调前移窗*(§2.3):`lag` 钳到 ≤0.6s 且缓慢自适应,对比目标**随播放持续前移**——你一旦定住,就被拿去和一个正在动的参考比,再也咬不住某一幸运帧。
- *活跃度门*:分别跟踪用户与参考的**平滑运动速率**,当参考在动而你几乎不动时,按不动程度最多打掉 90% 的分。两人**同时保持同一正确姿势不会被罚**(参考也没动),只罚"该动时你冻着":

```python
ur, rr = 用户本步转动量, 参考本步转动量   # 都做 EMA 平滑成"速率"
if self._rmot > MOTION_THRESH:            # 只在参考确实在动时启动
    deficit = clip(1 - self._umot / self._rmot, 0, 1)
    factor  = 1 - LIVENESS_STRENGTH * deficit   # 你越不动，扣得越狠
score *= factor
```

**修复 2 —— 覆盖度惩罚 + 缺帧计 0。** 分数乘以"参考正在用的手臂/腿里、你实际露出的比例";不可评帧记 0 并计入总评:

```python
ref_key = ok2 & KEY_LIMBS                       # 参考这一帧在用的手脚肢体
shown   = LIMB_WEIGHTS[both & KEY_LIMBS].sum()  # 你也露出的那部分
score  *= shown / LIMB_WEIGHTS[ref_key].sum()   # 藏腿 → 打折
```

**修复 3 —— 容差收紧 70°→50° + smoothstep**(§2.2):明显做错的肢体掉分更快,档位重新有意义。

**修复 4 —— 前缩肢体降权**:投影长度不足躯干 15% 的肢体按长度降权,"方向不可信就少信"。

### 4.4 量化验证(`validate_scoring.py` + 刷分对抗测试,均无需摄像头)

官方三项自检 **PASS**(用参考序列造已知真值的假用户):

| 测试 | 设置 | 结果 | 判定 |
|---|---|---|---|
| 空间不变性 | 同姿态,1.8× 体型 + 平移,无噪声 | 相似度 **100**,归一化差 **0.0000** | ✅ 位置/体型无关 |
| 时间对齐 | 匹配用户,注入 5 帧(167ms)延迟 | 恢复延迟中位数 **167ms** | ✅ 精确 |
| 匹配打分 | 1.4× 体型 + 平移 + 噪声 + 延迟 | 总分 **98.1 / PERFECT** | ✅ 该高则高 |
| 区分度 | 参考**反向播放**(错误动作) | 总分 **56.3 / GOOD**,差 40+ 分 | ✅ 明显更低 |

**刷分对抗测试**(修复前 vs 修复后):

| 场景 | 修复前 | 修复后 |
|---|---|---|
| **站着不动**(还从视频里挑姿势,对作弊者最有利) | **68.8 GOOD**(30 PERFECT + 166 SUPER) | **50.4 GOOD**,389 帧里 **208 帧判 X** |
| 真跳舞 | 97 | **98.2 PERFECT** |
| 只对上半身、藏腿 | ~98 | **67 GOOD** |

**诚实说明**:① 我们的"站着不动"是**对抗性最强**的版本——直接冻结在视频里出现过的姿势;真人两手自然下垂地站着与舞蹈差更远,分数只会更低。修复后它**总评仅 GOOD 且多数帧掉到 X**,不再是 SUPER。② 反向播放仍有 56 分而非 0,因为连续舞蹈倒放很多姿势仍相近(不是随机乱动);98 vs 56 的差距证明区分度真实存在。③ 容差停在 50° 而非更小,是**不为压对抗测试而过拟合**——真实摄像头噪声更大,过紧会误伤真跳舞的人。

## 5. 加分小游戏:神庙逃亡(细则第 16 题)

`temple_run.py`,独立 OpenCV 窗口,用全身体感控制。预览见 `task2_temple_run_preview.png`。

细则第 16 题三问,逐一回答:

### 5.1 能检测什么动作、用什么特征
三个手势,**全部基于最可靠的肩部关键点**(即使只有上半身入镜也能玩,这一点是踩过坑后的设计——近距离摄像头拍不全下半身):

| 动作 | 检测特征 | 游戏效果 |
|---|---|---|
| 左倾 / 右倾 | 肩部中心水平偏移 `dx=(sx−base_x)/肩宽`,超 ±0.45 | 切换三条跑道,躲单道石柱 / 选双格障碍的安全道 |
| 跳 | 肩部上移 `up>0.34` **或**上移速度 `vy>1.1 肩宽/秒` | 跳过横木低栏(JUMP) |
| 蹲 | 肩部下移 `dn>0.34` **或**下移速度 | 钻过拱门横梁(DUCK) |

阈值都以**肩宽为单位**归一化,对人离镜头远近免疫。启动时用约 1 秒"站直不动"标定基线(肩部中心+肩宽的中位数)。

**降低跳跃延迟**(实测反馈):跳是瞬间动作,原来只靠"位置越过阈值"会慢半拍。三处改进——(1) 游戏用的 `PoseTracker` **关闭时序平滑**(`smooth_alpha=1.0`),不为响应度买单;(2) 增加**速度触发**,肩部上移速度一超阈值就立刻判跳,抓住起跳瞬间而非等到最高点;(3) **动作锁存 0.35 秒**,让短暂的跳/蹲峰值稳定覆盖到障碍结算的那一刻。

**障碍类型**:单道石柱(换道躲)、**双格障碍**(两道被石柱挡住,只能移到唯一安全道——提供横向躲避策略)、横木低栏(跳)、拱门横梁(蹲);石柱做得足够高,一眼看出跳不过去,只能换道。

### 5.2 怎么渲染新物体
**第一人称透视走廊 + 真实美术贴图 + 滚动纹理背景**。世界用深度 `z` 建模(0=玩家处,大=远处),所有物体经**灭点投影**:`t=z/(z+K)`,近大远小 `scale=1−t`,跑道向灭点收敛。

**背景(`temple_bg.py`)**:无尽跑酷的运动感来自地面滚动而非背景视频。做法——代码**程序化生成无缝石砖/沙地纹理**,用 `cv2.remap` 在透视里采样,采样的深度坐标每帧随速度偏移,`BORDER_WRAP` 负责无缝平铺与滚动 → 地砖朝玩家涌来、向灭点收缩。地平线以上是**远景天幕**:放了 `assets/backdrop.*`(真实照片)就用它,没有则用渐变——远处几乎不动,静态照片在这里正合适。性能优化到 **~21ms/帧**(单次 `np.where` 合成 + 一次雾化混合,只在地平线以下的条带计算)。

**物体和角色**用 `assets/` 下的**透明 PNG 贴图**渲染——`blit()` 做 alpha 合成 + 按深度缩放 + 雾化:
- 主角三态(`player_run/jump/slide`,均**背后视角**),跳则腾空留地面阴影、蹲则滑铲贴地
- 石柱(带藤蔓)= barrier;横木 = hurdle;拱门 = overhang;金币、爱心(生命 HUD)、爆炸(受击)
- **优雅降级**:任一素材/纹理缺失都自动回退到内置绘制,不崩

预览见 `task2_temple_run_preview.png`。左侧摄像头缩略图叠骨架+当前动作,方便演示。

> 角色/物体素材是 CC0 卡通风(9 张,~15MB,已 gitignore);地面纹理是程序化生成、零素材。alpha 合成与 expert 任务的贴纸渲染同源。

### 5.3 怎么打分与流程
得分 = **存活距离/10 + 金币×10 + 躲过障碍×5**;被撞掉一条命(共 3 条),归零则 Game Over。障碍速度随时间缓慢加快。

**游戏流程有完整状态机**(实测反馈:原来一运行就开始、没缓冲):
`菜单(SPACE 开始)→ 标定(站直不动)→ 游戏中(P/SPACE 暂停)→ 结算界面`。
结束弹出**金币结算界面**:金币数×10、躲障碍数×5、距离/10 分项 + TOTAL 总分,SPACE 再来一局 / Q 退出。
